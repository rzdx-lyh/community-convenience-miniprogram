# 赛事差距分析

## 结论

现有工程 **不能直接作为本赛道省赛作品提交**。它是微信原生小程序，而赛道要求 AI Native Web 应用；同时 AI 部分更接近“知识库问答 + 可选大模型”，在 Agent、RAG、多模态和 MCP/工具集成上缺口明显。

## 评分差距

| 评分项 | 权重 | 当前能力 | 结论 |
| --- | ---: | --- | --- |
| 大模型集成质量 | 8% | 云函数可选 DeepSeek，缺少 Web 流式体验 | 部分具备 |
| Agent/工作流 | 8% | 无规划、工具调用、自主决策链 | 缺失 |
| RAG | 6% | 有关键词知识库检索，无向量检索与引用链 | 部分具备 |
| 多模态 | 5% | 无图片/语音识别 | 缺失 |
| AI 安全 | 4% | 已有风险规则、降级和兜底 | 基本具备 |
| MCP/工具集成 | 4% | 无 Function Calling/MCP | 缺失 |
| 创新性 | 25% | 社区场景真实，但交互模式传统 | 有场景，缺 AI 原生交互 |
| 前端工程 | 10% | 小程序 TypeScript 工程完整，但不是 Web | 形态不符 |
| 实用性 | 10% | 报修、地图、服务和三端账号有实际场景 | 较好 |
| 用户体验 | 10% | 适老化与三端入口已起步 | 需 Web 化重构 |
| 社会价值/商业潜力 | 10% | 社区便民、适老化价值明确 | 较强 |

## 必须补齐的能力

1. **独立 Web 前端**：建议 React + Vite 或 Next.js。
2. **AI Agent 工作流**：识别意图 → 规划 → 调用工具 → 返回结构化结果。
3. **RAG**：社区服务、通知、地图、电话簿、办事指南进入检索索引。
4. **多模态**：报修照片识别故障类型、风险和所需材料。
5. **Function Calling / MCP**：至少实现工具调用；优先实现 MCP Server 作为加分亮点。
6. **流式生成式 UI**：AI 回答流式渲染、工具调用状态、来源引用。
7. **公网演示地址**：供评审直接访问。
8. **完整赛事材料**：README、环境模板、PDF 技术文档、5–8 分钟视频、团队信息。

## 建议产品方向

推荐将现有“邻里百事通”升级为：

> **邻里 AI 办事管家：面向社区居民的 Agentic Web 服务入口**

核心不是聊天框，而是 AI 直接完成社区事项：

- 用户说“我家厨房漏水”，Agent 识别报修类型、查询服务点、创建工单、给出处理时限。
- 用户上传现场照片，多模态模型判断故障类别和紧急程度。
- Agent 检索社区公告、电话簿和办事指南，回答时给出引用。
- 用户问“最近哪里能借雨伞”，Agent 调用地图工具返回最近点位和路线。
- 高风险医疗/法律/紧急问题触发安全护栏并转人工。
