## 一、这是什么

一份**提示词与角色规范合集**——它不提供现成代码，它定义"**怎么问、怎么做、怎么交接**"。

把这 10 个 skill 文件分别喂给 AI（或团队各成员各认领一个角色），就能组成一条从需求到上线的完整流水线：

```
用户 → PM 拆解 → 产品 PRD → UI 设计 ──用户同意──> 架构师：契约 + 任务卡
                                                    ├─> 前端（并行）
                                                    └─> 后端（并行）
    前后端联调 → 合并 main → 测试 ──通过──> 运维部署 → PM 终审打包提交
```

**每个 skill 统一 14 章深度规范**：角色定位与职责边界 / 核心能力清单 / 激活时机与前置条件 / 可调用工具与用法 / **调查问卷** / 工作流程 / **交付物模板** / 质量标准与验收清单 / 交接协议 / 协作与沟通规范 / 与大赛评分对齐 / 常见坑 / 完整示例 / 完成前自检清单。

## 三、怎么用（三种姿势）

### 姿势 1：一个人 + AI（最快上手）

1. 先读 `skills/00-总提示词.md`，把它作为整段任务输入给 AI。
2. 想走哪一步，就把对应的角色文件喂进去（例如要写前端页面 → `05-前端工程师-skill.md`）。
3. 每个 skill **开工前会先输出一份调查问卷**，你答完它才动手——这一步不要跳过，答案质量决定产出质量。

### 姿势 2：多人分工（本项目实际采用）

三个人各认领一条线，靠 `contracts/` 里的契约对接：

| 角色 | 认领文件 | 负责产出 |
| --- | --- | --- |
| 集成 / 上线 owner（你） | `00-总提示词.md` + `04-架构师-skill.md` | 契约冻结、集成联调、上线打 tag |
| 前端工程师（同学 A） | `05-前端工程师-skill.md` | `miniprogram/` 全部页面与组件 |
| 后端工程师（同学 B） | `06-后端工程师-skill.md` | `cloudfunctions/` 全部云函数与 AI 集成 |

> 详细协作流程见仓库 `docs/09-三人分工与分支协作说明.md` 与两份派工单 `docs/10-*` / `docs/11-*`。

### 姿势 3：只取需要的部分

不需要整套流水线时，直接拿单个 skill 用。例如只要接口设计 → 只读 `04-架构师-skill.md` 的契约章节；只要测试 → 只读 `07-测试工程师-skill.md` 的用例模板。

## 四、六道用户闸门（不可跳过）

| 闸门 | 放行条件 |
| --- | --- |
| **G1** 方案拆解 | 用户说"同意"PM 的 WBS |
| **G2** 产品 PRD | 用户说"同意"PRD |
| **G3** UI 设计 | 用户说"同意"设计预览 |
| **G4** 契约与任务卡 | 用户说"同意"接口契约后**冻结，不得私改** |
| **G5** 测试通过 | 测试报告无 P0/P1 遗留 |
| **G6** 上线提交 | 22 项上线检查清单全绿 |

## 五、约定（省 token、少返工）

- 汇报一律"**摘要 + 文件路径**"，长内容写文件不刷屏。
- 问卷答案只问一次，落盘 `docs/00-问卷答案汇总.md`，全团队共享复用。
- 上下游之间**只传文件路径与结论**，不重复粘贴全文。
- 接口名一字不差：`workorder:list`（半角冒号），不是 `workorder.list`。
- 统一响应恒为 `{code, msg, data}`；错误码只用 0/400/401/403/404/429/500/503。

## 六、和正式仓库的关系

本 `skillpkg/` 是**只读分发包**，内容来自仓库根目录的 skill 文件与 `contracts/`、`docs/`。

**改动请改上游，不要改这里**——需要更新分发包时，重新执行打包即可，避免两份内容漂移。

> 与正式开发流程冲突时，一律以仓库 `contracts/api-contract.md` 为准。
