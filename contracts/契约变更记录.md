## CR-012 · `qa:ask` 高风险问题返回固定安全话术 + 可选出参 `_riskLevel`

### 背景（为什么要这条）

① 让大模型自由生成 —— 存在**医疗/法律误导风险**；
② 直接返回知识库原文 —— 知识库同样不具备专业资质，且可能给出过期/不适用内容。

### 🚫 `degraded=true` 的语义澄清（本次最重要的一条）

`degraded=true` **只表示"本次回答不是知识库的正常答案"，绝不等于"没有答案"**。它至少涵盖三种**都带着完整 `answer` 文本**的情形：

1. 高风险触发 → 固定安全话术（CR-012 新增）
2. 未命中 → 兜底话术 + 便民电话
3. LLM 失败 → 降级话术

**前端必须照常渲染服务端下发的 `answer`。**

| 场景 | `code` | 前端动作 |
| --- | :-: | --- |
| 未命中 / LLM 失败 | `0` + `degraded=true` | 降级态渲染 + 便民电话，**不 toast** |
| **命中安全话术** | `0` + `degraded=true` | **照常渲染 `answer` 全文**；降级引导卡文案由 `toDegradedTip(_riskLevel)` 决定，`_riskLevel !== 'none'` 时改为「以上为安全提示，社区无法提供专业医疗或法律意见」；**不 toast**；建议隐藏 👍/👎 反馈 |

**而 kb 里根本没有对应条目**——演示时点推荐问题，**第一条就撞兜底**。

**批准补充 6 条**（老年卡为刚需，因前端正在推荐它）：
老年卡与医保社保 / 停车与充电桩 / 快递与驿站 / 噪音与邻里纠纷 / 宠物与文明养犬 / 门禁与电梯卡。

**批准理由**：
1. 在后端可写范围内，**不动任何出参结构、不加字段、不加错误码**
2. **对真机 RAG 与 mock 应答双向收益**
3. 距截止十余天，晚做只增加风险；成本低至"一次自测的时间"

## CR-021-c · `qa:suggest` 统一到后端，且**每条必须有 kb 覆盖**

> ⛔ **推荐问题清单里的每一条，都必须能在知识库中命中。**
> 推荐一个自己答不上来的问题，等于**主动把兜底话术递到评委手上**。

现前端 3 条、后端 5 条是两套，且前端那套有未覆盖项。裁定：**统一到后端 `SUGGEST_QUESTIONS`**。

## CR-021-d · kb 副本治理

前端无法 import 后端 `cloudfunctions/shared/kb/kb.json`，**前端 kb 必然是副本**。

| 方案 | 结论 |
| --- | :-: |
| ✅ **首选：脚本生成** | 构建步骤中加入「`shared/kb/kb.json` → `miniprogram/mock/kb.json`」复制——**与 seed 引 `hotline.js` 同一套路**，漂移物理上不可能发生 |
| ⚠️ 退回：断言锁死 | 无构建步骤时，必须断言「前端 kb 条数 == 后端条数，且 `id` 集合一致」，并在文件头标注同步责任 |

否则 kb 将成为**第三份漂移副本**，CR-020-c 的「三角」会变成**四角不一致**。

## CR-022 · 新增服务分类承接页（38 项）

- **日期**：2026-10-18
- **提出**：前端（FE-14）
- **状态**：✅ 已生效（代码已实现，`app.json` / `api-contract.md` 附 A.2 已同步）

### 变更内容

| 项 | 变更前 | 变更后 |
| --- | --- | --- |
| `app.json.pages` | 9 个页面 | **10 个**，新增 `pages/service/category/index` |
| `service:list` 返回结构 | 4 类 / 10 子项（`items`） | 4 类 / **8 板块 / 38 子项**（`items` + `groups`） |
| 宫格点击行为 | `wx.showActionSheet` 展开子项 | `navigateTo` → 服务分类页 |
| 预约提交 | — | 复用 `workorder:create`（`category='other'`） |

### 原因

CR-008 的「**不新增任何页面**」裁定，前提是子项只有 8 个，ActionSheet 一屏能放下。
设计原型把服务扩到 **38 项 / 8 板块**后：

1. ActionSheet 一屏塞不下 38 行，滚动列表在 iOS 上还可能被截断；
2. ActionSheet 只能显示名称，没有「60 元/小时起」这类说明，用户无从判断；
3. 38 项若各建一个表单页，才是真正的时间黑洞。

### 取舍：只加 1 个页面，而不是 4 个

| 方案 | 页面数 | 工期 | 结论 |
| --- | :-: | --- | --- |
| CR-008 原方案（4 个承接页） | +4 | +2.5~3 天 | ❌ 已被 CR-008 否决，本次也不采用 |
| **本次方案**：1 个分类页 + 页内预约弹层 | **+1** | +0.5 天 | ✅ 采用 |
| 全用 ActionSheet | 0 | 0 | ❌ 38 项不可用 |

预约表单做成**分类页内的弹层**，而不是独立表单页：11 个需要预约的服务共用一套
「选项 / 房号 / 期望时间 / 备注」表单，提交走既有 `workorder:create`。

- **前端 A**：新增 1 页 4 文件；首页 `onGridTap` 改跳转（保留 ActionSheet 作为 `navigateTo` 失败的兜底）；`service-grid.ts` 数据从 10 项扩到 38 项并引入 `groups`；`SEARCH_ALIASES` 从 26 条扩到 100+ 条以覆盖 38 项的口语说法。
