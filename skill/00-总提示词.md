## 一、项目一句话

为「数创铸魂·码承文脉」广演小程序/移动应用开发大赛暨第二届讯方杯技能大赛，开发一款**社区便民微信小程序**：让居民"**报修有人管、办事有人答、电话随手查**"，并面向老年人做**适老化**（大字 + 语音），最终产出可演示作品 + 全套参赛材料。

### 作品定位三要素
| 要素 | 内容 |
| --- | --- |
| 目标用户 | 社区居民（重点含老年人）、物业人员、社区网格员 |
| 核心场景 | ①故障报修（AI 辅助）②社区办事咨询（AI 问答）③便民电话查询 ④通知/活动触达 |
| 差异化卖点 | **AI 问答真解决问题**（RAG 知识库，非概念贴标签）+ **适老化关怀模式** + **岭南文化视觉元素** |

## 七、Git 分支策略（多人协同）

| 分支 | 用途 | 谁提交 | 规则 |
| --- | --- | --- | --- |
| `main` | 主干（稳定可演示） | 仅合并（PR/merge） | 受保护；只接受联调通过后的合并；合并后打 tag `v1.0.0` |
| `feature/frontend` | 前端开发 | 前端工程师 | 提交前先 `git pull/merge main` 同步 |
| `feature/backend` | 后端开发 | 后端工程师 | 同上 |

**标准操作序列**
```bash
# 首次从主干切分支
git switch main && git pull
git switch -c feature/frontend      # 或 feature/backend

# 日常提交（小步多次）
git add -A && git commit -m "feat(repair): 报修创建页完成图片上传"

# 开工前同步主干（分支落后会导致冲突）
git fetch && git merge main

# 联调通过后合并回主干
git switch main && git merge feature/frontend && git merge feature/backend
git tag v1.0.0
```

**冲突处理**：两个人改同一文件→以契约为准，架构师裁决；共享工作区多人切换分支会互相影响，**分支操作按顺序持有**（或用独立克隆目录）。

## 十一、省 token 规则（用户明确要求）

1. 汇报用"**摘要 + 文件路径**"，长内容写文件，不刷屏。
2. 问卷**只问一次**，答案汇总到 `docs/00-问卷答案汇总.md`，全团队复用，下游不得重复提问。
3. 环境事实已在第六节列明，**禁止重复问用户**。
4. 上下游交接只传文件路径 + 结论，不粘贴全文。
5. 用户不回复时保持待命，**不得空转产出**（避免无效消耗）。

## 十二、常见问题与应对（FAQ）

| 问题 | 应对 |
| --- | --- |
| 用户不回答问卷 | 保持待命，一次提醒；不擅自替用户决策（除已在环境事实中确认的项） |
| 时间只剩 12 天，做不完 | 砍 P2 功能，保 P0 主干（报修 + AI 问答 + 电话簿 + 通知）；UI 用组件化，视觉简化 |
| 没有云开发环境 ID | 走 mock 双通道开发，request 层开关切换；上线前再申请环境 |
| 没有大模型 API Key | AI 接口实现降级路径（兜底话术 + 电话），不阻塞开发；申请到 Key 后切真调用 |
| AI 回答质量差/幻觉 | 强化 Prompt（限定知识库范围、要求无命中就说不知道）+ RAG 检索阈值 + 兜底话术；测试阶段专门评测 20 题 |
| 微信审核不过 | 类目选"生活服务-社区服务"；隐私协议在 mp 后台填写；避免医疗建议等敏感表述 |
| 多人协作冲突 | 契约唯一 + 分支隔离 + 分支操作按顺序持有；冲突由架构师裁决 |
| 演示现场断网 | 准备 3 分钟以上录屏备份；AI 降级路径可现场演示"无网也有兜底" |
| 往届作品复用是否违规 | 允许迭代升级，但必须在《历史说明》章节明确标注优化部分，不得直接当新作品提交 |
| 材料被形式审查退回 | 按第九节命名规范打包，核对 7 项材料清单与 300MB 限制 |
