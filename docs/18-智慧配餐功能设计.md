# 18 · 智慧配餐功能设计（v1.1.0）

> 需求原文：`加一个智慧配餐，就是提供健康的膳食搭配`
> 交付物：`docs/03-preview/demo.html`（v1.1.0，唯一入口，历史路径已同步）
> 自测：48 条断言全绿（`.workbuddy/_t11.mjs`）

---

## 1. 为什么是"第 6 种页面原型"而不是再画一个表单

v1.0.9 已经把服务页拆成 5 种骨架，判断依据是**用户要做的判断类型**：

| 原型 | 用户的判断 | 典型页面 |
|---|---|---|
| P1 向导型 | 一步步选完才能提交 | 保洁、助浴、挂号 |
| P2 票据型 | 看一个号码、出示它 | 快递代收 |
| P3 数据型 | 判断我这组数字好不好 | 健康档案 |
| P4 卡片流 | 从一堆同类项里找一项 | 缴费、租房 |
| P5 设备型 | 现在能不能借、还剩多久 | 共享雨伞、充电宝 |

智慧配餐**不属于这 5 种**。它的动作顺序是：

```
配置（目标/人数/忌口） → 系统生成一份方案 → 在方案上迭代（换菜/锁定）
```

前 5 种都是"**填完 → 提交 → 结束**"；配餐是"**先生成结果，再改结果**"。因此定义为 **P6 组合型**，两个页面共用一个状态机。

**设计上的关键取舍**：不做"营养计算器"（让用户自己填每样吃多少），而是**给一份可以直接照着买菜的方案**。理由是——个人主体小程序 + 老年人场景，用户要的是"今天吃什么"，不是"热量怎么算"。

## 2. 页面结构

### 2.1 设置页 `mealSetup()`

首次进入（`state.meal.onboarded === false`）自动落在这一页。

```
┌ 沉浸头（青绿 #1FA97A → #0B6146）
│  ‹ 智慧配餐                    怎么算的 ›
│  🥗 先告诉我你要吃成什么样
│     按目标生成一周三餐
├ 配餐目标（单选，5 个 .opt 大选项）
│  ✓ 控糖   低 GI · 少精制糖
│    控压   低钠 · 高钾
│    减脂   高蛋白 · 控油
│    术后恢复 高蛋白 · 易消化
│    老年软食 软烂 · 少骨刺
├ 用餐人数（4 个 .dchip）
│  1 人 独居 | 2 人 两口 | 3 人 三口 | 4 人 多人
├ 忌口（5 个 .chip，可多选）
│  素食 海鲜 牛肉 蛋奶 辛辣
├ 说明条：按《中国居民膳食指南》配比生成，热量为参考值
└ fbar：控压 · 3 人份 / 目标 1700 kcal · 钠 1300 mg   [生成一周配餐]
```

**底部固定条 `.fbar` 是实时的**：改目标、改人数，`sum` 行立刻跟着变。这是让用户还没生成就知道"我会得到什么标准"。

### 2.2 方案页 `pgMeal()`

```
┌ 沉浸头（同上青色系）
│  ‹ 智慧配餐                    改目标 ›
│  今日能量 · 控压方案            今天 · 3 人份
│  1560 / 1700 kcal              钠 1420 / 1300 mg  [食材清单 ›]
├ .dash 白卡：能量环 + 三根营养素条
│   ◯ 92%         蛋白 ████░░ 78 / 76 g
│    热量达成      碳水 ███░░░ 196 / 221 g
│                 脂肪 ████░░ 52 / 57 g
├ .wkr 7 天日期条（今天/明天/周二…周六，带 10-18…10-24）
├ .dish 早餐卡（蓝色餐次标）
│   🥣 小米南瓜粥 + 拌黄瓜
│      碳水 42g · 脂肪 4g · 钠 180mg
│      [低GI] [软食] [素食]
│   🔄 换一道        🔓 锁定
├ .dish 午餐卡（青色餐次标）
├ .dish 晚餐卡（金色餐次标）
├ 免责声明（居中，9px）
└ fbar：3 人份 · 控压 / 今日三餐 1420 kcal   [预约助餐]
```

**能量环是 `conic-gradient`**，用 `--p` 变量驱动，不用 canvas：

```css
.mring{width:110px;height:110px;border-radius:50%;
  background:conic-gradient(var(--mc) calc(var(--p)*1%),#EDF1F6 0);}
.mring::after{content:'';position:absolute;inset:9px;border-radius:50%;background:#fff;}
```

## 3. 数据模型

### 3.1 配餐目标 `MEAL_GOALS`

| key | 名称 | 策略 | 色 | 日热量 | 钠上限 |
|---|---|---|---|---|---|
| `sugar` | 控糖 | 低 GI · 少精制糖 | `#1F5FD6` | 1600 kcal | 1600 mg |
| `bp` | 控压 | 低钠 · 高钾 | `#C9302C` | 1700 kcal | **1300 mg** |
| `fat` | 减脂 | 高蛋白 · 控油 | `#0E7C6B` | **1400 kcal** | 1800 mg |
| `post` | 术后恢复 | 高蛋白 · 易消化 | `#A86A05` | 1800 kcal | 1500 mg |
| `elder` | 老年软食 | 软烂 · 少骨刺 | `#4B45B8` | 1500 kcal | 1400 mg |

`GOAL_TAG` 把目标映射到一个菜品标签，用于**排序优先**（不是硬过滤）：`sugar→低GI`、`bp→低钠`、`fat→高蛋白`、`post→软食`、`elder→软食`。

### 3.2 菜库 `DISHES`（15 道）

- 三餐各 5 道：`b1–b5`（早餐）、`l1–l5`（午餐）、`d1–d5`（晚餐）
- 每条字段：`{id, meal, n, e, kcal, p, c, f, na, tags, ing}`
  - `meal`: `b|l|d`；`n`: 菜名；`e`: emoji；`tags`: 标签数组；`ing`: 食材数组
- 标签集合：`低GI / 低钠 / 高蛋白 / 软食 / 素食 / 海鲜 / 牛肉 / 蛋 / 奶 / 豆制品`

**忌口 ↔ 标签的硬过滤关系**（`dishOk`）：

| 忌口 | 剔除条件 |
|---|---|
| 素食 | 菜品**没有** `素食` 标签 → 剔除 |
| 海鲜 | 有 `海鲜` 标签 → 剔除 |
| 牛肉 | 有 `牛肉` 标签 → 剔除 |
| 蛋奶 | 有 `蛋` 或 `奶` 标签 → 剔除 |
| 辛辣 | 有 `辛辣` 标签 → 剔除 |

> 素食是**反向**判断（必须白名单命中），其余是命中即剔除。这一条在自测里专门验了：勾"海鲜"后午餐不能出现"清蒸鲈鱼 / 清炒虾仁"。

### 3.3 状态

```js
meal:{
  onboarded:false,       // 是否已生成过
  goal:'sugar',          // 目标 key
  people:2,              // 人数 1-4
  taboos:[],             // ['素食','海鲜',...]
  day:0,                 // 当前查看第几天（0-6）
  plan:{ '0_b':'b3', ... },  // 已固定的菜，key = `${day}_${slot}`
  locked:{ b:false, l:true, d:false }  // 锁定的餐次
}
```

`plan` 只存**被改过或生成时定下的**项；没有记录的会自动用 `pickDish(slot, day, ...)` 现算。这样切到第 4 天不需要预先算 7×3=21 个格子，按需生成即可。

## 4. 核心算法

### 4.1 选菜 `pickDish(slot, idx, meal, goal)`

```
pool = DISHES.filter(meal === slot && dishOk(d, meal))
pool.sort( 命中 GOAL_TAG 的排前面 )          // 稳定排序，同组内保持原顺序
if pool 为空 → 回退到全部该餐次菜品（防忌口过严导致空列表）
return pool[idx % pool.length]
```

`idx` 用 `%` 而不是随机——保证**同一天同一餐次每次渲染结果一致**，否则每次 `render()` 菜都会变，用户会觉得系统抽风。

### 4.2 换一道 `swapDish(slot)`

```
if locked[slot] → toast('这一餐已锁定，先解锁再换'); return
pool = 忌口过滤后的同餐次菜品
cur  = plan[day_slot] 或当前渲染出的那道
next = pool[(indexOf(cur) + 1) % pool.length]     // 循环轮换
plan[day_slot] = next.id; render(); toast('已换成：' + next.n)
```

**为什么是循环轮换而不是随机**：5 道菜最多点 5 次就会转一圈，用户能预期"再点会回到刚才那道"，不会觉得在赌博。当前菜不在 pool 里（比如改了忌口）时 `indexOf` 返回 -1，`(-1+1)%len = 0`，自动落到第一道——是个安全的兜底。

### 4.3 能量配比

三大营养素目标值按热量反推（不是固定克数）：

```js
const pt = Math.round(g.kcal * 0.18 / 4);   // 蛋白 18%，4 kcal/g
const ct = Math.round(g.kcal * 0.52 / 4);   // 碳水 52%，4 kcal/g
const ft = Math.round(g.kcal * 0.30 / 9);   // 脂肪 30%，9 kcal/g
```

以控压 1700 kcal 为例：蛋白 77g / 碳水 221g / 脂肪 57g。

达成率 `pct = round(sum.kcal / g.kcal * 100)`，环上封顶 100%（但数字照实显示，超过 100% 就不说谎）。

## 5. 交互细节

| 动作 | `data-act` | 行为 |
|---|---|---|
| 选目标 | `meal-goal` | 改 `goal`，重渲染（选项上出 ✓） |
| 选人数 | `meal-people` | 改 `people`，fbar 实时更新 |
| 勾忌口 | `meal-taboo` | 数组增删，chip 高亮 |
| 生成 | `meal-start` | `genMealPlan()` → `onboarded=true`，toast 带目标名 |
| 改目标 | `meal-reset` | `onboarded=false`，回到设置页（保留已选条件） |
| 切日期 | `meal-day` | 改 `day`，**清空 `locked`**（换天不该继承锁定） |
| 换菜 | `meal-swap` | `swapDish(slot)` |
| 锁定 | `meal-lock` | 翻转 `locked[slot]`，按钮文案 🔓↔🔒 |
| 食材清单 | `meal-list` | 弹层：三餐食材去重 + ×N |
| 一键下单 | `meal-buy` | 关弹层 → `state.page='fresh'`，`freshTab='veg'` |
| 预约助餐 | `meal-order` | 弹层登记（份数/时段/补贴说明）+ 确认 |
| 怎么算的 | `sheet-meal-help` | 弹层：4 条公式 + 免责声明 |

**「改目标」不重置已选条件**是有意的：用户往往只是想换个目标对比一下，不该让他把人数和忌口重填一遍。

## 6. 合规红线（个人主体小程序）

这是全项目**风险最高的一个功能**——一旦写成"治病"就踩了《广告法》和互联网诊疗的红线。已执行的约束：

| 禁止 | 已替换为 |
|---|---|
| 治疗 / 疗效 / 降血糖 / 降血压 | 控糖 / 控压 / 建议 / 参考值 |
| "适合糖尿病患者" | "控糖方案"（描述饮食结构，不描述疾病） |
| "营养处方" | "配餐方案 / 膳食建议" |

页面上的三处免责声明：

1. 设置页说明条：「按《中国居民膳食指南》配比生成，热量为参考值；有慢性病请以签约医生意见为准。」
2. 方案页底部：「配餐依据《中国居民膳食指南（2022）》与目标人群能量需求估算；菜品可按忌口自动替换，仅供参考，**不替代医生或营养师处方**。」
3. 「怎么算的」弹层底部（金色警示条）：「以上为膳食建议，不替代医生或营养师处方；糖尿病、肾病、术后患者请遵医嘱。」

**没有做的事**（也是刻意的）：
- 不采集血糖/血压数值做个性化计算（涉及健康数据处理，个人主体过不了）
- 不做"疗效承诺"或"打卡改善"类文案
- 不接入任何第三方营养数据库 API（数据来源不可控 = 合规风险不可控）

## 7. 小程序落地映射

### 7.1 页面拆分

原型是单页状态机，真机建议拆 2 个页面 + 2 个自定义组件：

```
pages/meal/setup/index    设置页（目标/人数/忌口）
pages/meal/plan/index     方案页（能量环/日期条/菜品卡）
components/meal/dish-card 菜品卡（含换菜/锁定）
components/meal/ring      能量环（canvas 或 conic-gradient）
```

### 7.2 云函数接口

```
POST cloud function: meal
  action: 'plan'   → { goal, people, taboos, week }  返回 7 天 × 3 餐
  action: 'swap'   → { goal, people, taboos, slot, cur } 返回下一道
  action: 'order'  → { people, slot, goal } 写入助餐登记表
```

**菜库放云函数侧**（`meal-data.js`），不放前端：改菜谱不用发版，也避免前端包体膨胀。前端只留 `MEAL_GOALS` 常量（用于渲染目标选项和热量标准）。

### 7.3 数据表

```
meal_order: {
  _openid, goal, people, taboos[], slot, date,
  status: 'registered' | 'delivered',
  createdAt
}
```

和现有「只登记不支付」的口径一致，费用到餐时结算。
