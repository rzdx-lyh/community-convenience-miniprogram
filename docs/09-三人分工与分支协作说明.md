# 三人分工与分支协作说明

> 适用项目：社区便民微信小程序（大赛「数创铸魂·码承文脉」，提交截止 2026-10-25 23:59）
> 角色：**你 = 主分支 owner（集成/联调/上线负责人）**；同学 A = 前端工程师；同学 B = 后端工程师。
> 本文件是三人协作的操作手册，与 `contracts/api-contract.md` 冲突时以契约为准。

---

## 0. 一句话结论

三个人**三个独立工作目录、三条开发分支**：同学 A 只写 `feature/frontend`，同学 B 只写 `feature/backend`，你在 `staging`（临时缓存/集成分支）做缓存作业与上线验证；验证通过后 `staging` 合并进 `main`。**任何人不许直接往 main 提交代码。**

## 1. 「临时缓存区」怎么落地（分支策略）

### 1.1 为什么需要缓存区

- `main` 是**最终交付态**（要能稳定演示、要打 tag、要被评委看），不能拿来试错。
- 两位同学并行开发，代码天生是半成品，直接进 main 会污染交付历史。
- 缓存区（`staging`）的作用：**把两边的半成品先合并到一起联调、跑通、上传体验版验证，确认"上线没问题"再一次性进 main。**

### 1.2 推荐分支模型（4 条分支）

| 分支 | 归属 | 用途 | 谁能提交 |
| --- | --- | --- | --- |
| `main` | 你 | 最终稳定态、交付打包、打 tag `v1.0.0` | 只接受 `staging` 合并，**禁止直接推送** |
| `staging` | 你 | **临时缓存区**：集成两端代码、联调、上传体验版验证 | 只有你 |
| `feature/frontend` | 同学 A | 小程序前端全部代码 | 只有同学 A |
| `feature/backend` | 同学 B | 云函数后端全部代码 | 只有同学 B |

> 注：skill 包原始设定是「3 条分支、联调后直接 merge main」。本文件在原设定上**增加一条 `staging` 作为缓存/集成区**，是更稳妥的做法。这意味着 skill 包里的分支表述与现状有差异——后续若统一改名/补分支，需同步修改文档（见 §7）。

### 1.3 工作区隔离（**这一步最关键**）

skill 包里明确记录了往期事故：**8 人共用同一目录，谁切分支都会改变别人眼前的文件**。

**铁律：三人各自一个目录，禁止共用同一个 .git 工作区。**

三种做法任选：

| 做法 | 命令 | 适用 |
| --- | --- | --- |
| 独立克隆（推荐） | `git clone <仓库> ../fe-work` | 三台机器或三个目录 |
| Git worktree | `git worktree add ../fe-work feature/frontend` | 同一仓库多目录，共享 .git 但互不干扰 |
| 同一目录（**不推荐**） | 按顺序持有工作区 | 只有实在没法分目录时，且必须"谁用谁锁" |

> 当前 `main` 已被 `C:/Users/Administrator/Desktop/code/ai web/Community Convenience Services` 这个工作区占用；本 WorkBuddy 工作区在 `workbuddy/main-c47d81ed`。

### 1.4 完整命令序列

```bash
# ---------- 你：先建缓存/集成分支（在 main 工作区执行一次） ----------
git switch main
git pull
git switch -c staging

# ---------- 同学 A：前端 ----------
git clone <仓库> fe-work && cd fe-work
git switch main && git pull
git switch -c feature/frontend

# 日常提交（小步多次，一卡一提交）
git add -A && git commit -m "feat(FE-4): 报修列表页完成分页与筛选"
# 开工前先同步 main，防落后
git fetch && git merge main --no-edit

# ---------- 同学 B：后端 ----------
git switch main && git pull
git switch -c feature/backend
git add -A && git commit -m "BE-2: 工单创建/列表/详情云函数"
git fetch && git merge main --no-edit

# ---------- 你：缓存区集成（联调） ----------
git switch staging
git merge feature/frontend --no-edit
git merge feature/backend --no-edit
# 跑通联调 + 上传体验版验证
& "D:\app\微信\开发小程序\微信web开发者工具\cli.bat" upload --project "<staging 工作区路径>" --version 0.9.0 --desc "staging 联调验证"

# ---------- 你：验证 OK 后进 main ----------
git switch main
git merge staging --no-edit
git tag v1.0.0
```

**冲突处理**：以契约为准，改同一文件谁先谁后由你（main owner）裁决；冲突时优先保留契约一致的一侧，另一侧改动到 `contracts/联调问题清单.md` 记录。

你是**集成与交付总闸门**，不写业务页面/云函数，但要对"能不能上线"负总责：

| # | 事项 | 说明 |

### 4.1 他是谁 / 边界

- **负责**：`cloudfunctions/` 全部云函数（auth/workorder/notice/phonebook/qa 五个资源分组）、`scripts/`（种子数据、知识库、自测）、`docs/06-后端自测记录.md`。

**开工必读**：`contracts/api-contract.md`、`db-schema.md`、`task-cards.md`、`docs/04-架构设计.md`、`docs/02-产品方案PRD.md`。

**开工第一动作**：`git switch feature/backend` → 确认干净 → 与 main 对比。

### 4.2 降级铁律（本项目最重要的后端纪律）

> **无云开发环境、无 AI Key，也必须让全部接口跑通。**

- 无云环境 → `shared/db.js` 自动切本地 mock DB（内存集合），API 面与云数据库一致。
- 无 Key → `shared/ai.js` 立即返回 `{ degraded: true, content: '' }`，**不发请求、不抛错**；qa 走知识库原文或兜底话术。
- 无订阅模板 ID → 只记 `[degraded]` 日志，接口照常成功。

### 4.3 任务卡（BE-0 ~ BE-8），共 9 张

| 卡 | 内容 | 依赖 | 验收要点 |
| --- | --- | --- | --- |
| **BE-0** | 工程与基础层：`cloudfunctions/` 目录 + shared 公共层（响应/错误码/时间/DB 适配/鉴权/安全/订阅/AI/Prompt/知识库）+ `scripts/seed.mjs` | 无 | 统一响应符合契约；种子脚本可跑通 |
| **BE-1** | auth 分组：login / updateProfile | BE-0 | 首次登录自动建档；手机号 AES 加密；越权 403 |
| **BE-2** | workorder：create / list / detail | BE-0、BE-1 | 创建接 msgSecCheck；AI 摘要失败不阻断；列表按角色隔离；分页正确 |
| **BE-3** | workorder：cancel / handle | BE-2 | 取消仅本人+pending；状态机流转正确；done 触发订阅消息（无模板 ID 降级日志） |
| **BE-4** | notice：list / detail | BE-0 | 仅返回 published；详情 404 处理 |
| **BE-5** | phonebook：list | BE-0 | 按 sort 升序；分类过滤 |
| **BE-6** | qa：ask / feedback / suggest（**AI 核心**） | BE-0 | 问答链路通；无 Key 降级正常；AI 耗时日志 |
| **BE-7** | 知识库初始化脚本：首批资料整理为 JSON，`scripts/kb.mjs` 导入 | BE-0 | 知识库含 **≥10 条问答对** |
| **BE-8** | 联调与自测：按契约逐接口自测，产出 `docs/06-后端自测记录.md` | BE-1~7 + FE | 契约内接口全部按入参/出参/错误码验证通过 |

**关键技术约定**：
- 统一响应恒为 `{code, msg, data}`，**无裸返回**；错误码只用契约表（0/400/401/403/404/429/500/503）。
- 鉴权取 `wxContext.OPENID`（不可伪造），写操作走 `requireStaff`。
- 分页：`page` 从 1 起，`pageSize` 默认 10 上限 50，返回 `{list, total}`。
- 时间一律 `toISOString()`（ISO8601），**禁止时间戳数字**。
- 状态机：`pending→assigned→processing→done`；非法流转 400。
- AI 超时 **8s、失败不重试、直接降级**；日志含 `cost_ms`。
- 手机号 AES-256-GCM 加密入库、出参脱敏 `138****1234`。
- **密钥只走环境变量**（`DEEPSEEK_API_KEY` / `TCB_ENV` / `PHONE_AES_KEY` / `SUBSCRIBE_TEMPLATE_WORKORDER_DONE`），**永不进代码、永不进 git**（提交前 `git grep -i "sk-"` 自查）。

**交付物**：`cloudfunctions/` + `scripts/`（seed.mjs / seed-data.json / kb.mjs / selftest.mjs / mock-server.mjs）+ `docs/06-后端自测记录.md`。

## 6. 协作节奏

```
同学A: feature/frontend ──┐
                          ├─→ 你: staging 集成联调 ──→ 上传体验版验证 ──→ main (tag v1.0.0)
同学B: feature/backend  ──┘
```

1. **起步**：你分发契约 → 两人各自切分支、各读必读文件。
2. **并行**：A 按 FE-0→FE-10 逐卡开发；B 按 BE-0→BE-8 逐卡开发。**各自 mock 自测**，不被对方卡住。
3. **集成**：A/B 各自完成后通知你 → 你把两端 merge 进 `staging` → 开联调（`USE_MOCK=false`）。
4. **验证**：`staging` 上传体验版 → 真机走 P0 主链路（报修 + AI 问答 + 电话簿 + 通知）。
5. **上线**：验证 OK → `staging` 合并 `main` → 打 `v1.0.0` → 进入测试/部署。

**每卡完成的标准汇报格式**（三人统一）：
```
【角色】任务卡 FE-4 完成。产物：miniprogram/pages/repair/list/。
自测：渲染✓ 交互✓ 接口✓。提交：feature/frontend <hash>。下一步：FE-5。
```

## 7. 风险与坑（提前打预防针）

| 风险 | 规避 |
| --- | --- |
| **三人共用目录切分支互踩** | 铁律：三个独立目录（clone 或 worktree） |
| **feature 分支落后 main** | 开工前 `git log --oneline -1 main` 对比，落后就 `git merge main --no-edit` |
| **前端忘切 mock 开关** | 联调第一天第一件事：确认 `USE_MOCK=false` |
| **后端无 Key 就停摆** | 降级铁律：无 Key/无云环境也必须全接口跑通 |
| **密钥进 git** | 提交前 `git grep -i "sk-"` / `git grep -i "secret"` 必须干净 |
| **契约被私改** | 只有你能批；改前更新契约并登记《契约变更记录》 |
| **skill 文档与现状不一致** | skill 包写的是「3 条分支、联调后直进 main」；本文件新增 `staging` 并把角色并到 2 人。**后续若正式改名/定稿，需同步更新 `README.md`、`00-总提示词.md`、`docs/00-环境与资源速查.md`、`contracts/task-cards.md` 等处的分支表述。** |
