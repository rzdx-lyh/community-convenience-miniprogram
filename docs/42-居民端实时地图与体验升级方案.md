> 文档版本：v1.0
> 编写日期：2026-11-09
> 当前代码基线：v1.2.7
> 项目定位：非盈利社区便民工具，重点服务赛事演示与比赛材料准备
> 状态：方案设计，本轮不修改代码
> 关联文档：`37-定位接口被拒后的替代方案.md`、`40-AI识图与方言转换方案.md`、`41-三端权限与工单流程方案.md`

## 1. 结论先行

建议在居民端增加一套 **“双轨社区实时地图”**：

1. **基础模式（始终可用）**
   保留当前 6 个楼栋/出入口手选位置、9 个社区服务点、距离计算和 `wx.openLocation` 导航。即使定位权限被拒绝，地图功能仍然完整可用。

2. **实时模式（权限获批后启用）**
   用户主动点击「定位到我的位置」后，调用微信位置接口获取当前位置，在地图上显示定位点，并实时重算附近服务点距离。必要时可开启前台连续定位，但离开地图页立即停止，不做后台追踪。

推荐技术路线：

> **微信原生 `<map>` 组件 + `wx.getLocation` 单次定位 + 可选前台持续定位 + 本地 POI/Haversine 距离计算。**

首期**不需要百度地图 API，也不需要腾讯位置服务 Key**。微信原生地图组件已经能完成底图、点位、气泡、定位点、缩放和内置地图导航。

只有后续确实需要“地址逆解析、社区外 POI 搜索、路线规划、关键词联想”时，再增加腾讯位置服务作为可选增强；百度地图不作为首选。

**重要结论：**

- 微信位置接口是免费能力，但需要满足开放类目并在微信管理后台单独申请，审核通过后才能稳定调用。
- 本项目 2026-10-24 申请 `wx.getLocation` 曾被驳回，原因是使用场景未符合开放范围。
- 当前项目文档显示主体为个人主体，服务类目为「工具 > 信息查询」。该类别出现在微信官方开放类目列表中，但不代表一定审核通过；重新申请仍以微信后台审核结果为准。
- 更换百度或腾讯地图供应商**不能绕过微信位置权限**。第三方地图只解决地图、POI 和路径数据，不能替代 `wx.getLocation` 获取手机当前位置。
- 非盈利和赛事用途可以作为申请说明，但不会自动豁免接口审核。
- 首期应当把实时定位视为增强能力，把“手动选楼栋 + 静态服务点地图”视为赛事演示的保底路径。

## 2. 当前源码审计结论

### 2.1 页面与组件规模

本次浏览了居民端页面、配置、服务层、样式、地图、AI 助手、关怀模式和测试守卫，主要规模如下：

| 项目 | 当前情况 |
| --- | ---: |
| 已注册页面 | 34 个 |
| 底部 Tab | 4 个：首页、办事、圈子、我的 |
| 服务类子页面 | 15 个 |
| 公共业务组件 | 2 个：`ai-bar`、`empty-state` |
| 地图点位 | 9 个 |
| 手动社区位置点 | 6 个 |
| 自动化测试 | 28 个文件、355 条通过 |
| Lint | 0 error、7 个 `any` 类型 warning |

### 2.2 定位与地图现状

当前地图实现位于：

```text
miniprogram/pages/map/index.ts
miniprogram/pages/map/index.wxml
miniprogram/config/community.ts
miniprogram/utils/geo.ts
```

现状：

- 使用微信原生 `<map>` 组件。
- 使用 9 个本地静态 POI。
- 用户通过 `wx.showActionSheet` 手动选择 3 号楼、1 号楼、南门、西门等社区位置。
- 通过 Haversine 公式计算距离，按步行时间排序。
- 使用 `wx.openLocation` 打开微信内置地图导航。
- 没有调用 `wx.getLocation`、`wx.startLocationUpdate`、`wx.onLocationChange`。
- 没有使用 `show-location`。
- `tests/location-policy.test.ts` 目前明确禁止重新加入定位调用，这是上一轮审核驳回后的保护措施。

### 2.3 可以直接改善的体验问题

#### 页头不统一

当前页面至少存在多套顶部结构：

- `sbar + nav`
- 彩色 `pgh` 页头
- 自定义内嵌返回按钮
- 无独立页头但保留返回逻辑

结果：

- 状态栏、胶囊避让和返回按钮位置容易不一致。
- 关怀模式下字号放大后，页头更容易拥挤或错位。
- 新页面继续复制旧页头，会持续增加维护成本。

#### 服务页重复度高

15 个服务子页面大多重复以下结构：

```text
页头
→ 筛选或分类
→ 卡片列表
→ 详情弹层
→ 姓名/电话/楼栋/备注表单
→ 提交按钮
→ 成功凭证
```

但每页都各自实现了一套 WXML、WXSS 和提交逻辑，导致：

- 相同表单在不同页面样式不一致。
- 空态、加载态、错误态各写各的。
- 修改一个交互要改多个页面。
- 页面看起来“功能很多”，但实际流程高度重复。

#### 空态组件复用不足

项目已有 `components/empty-state`，但目前主要在报修列表使用，多个页面仍在手写“暂无内容”“没有找到”等空态。

建议统一为：

```text
加载中
空数据
请求失败
定位失败
权限被拒绝
离线降级
```

#### 首页信息密度偏高

首页同时有：

- 定位胶囊
- 搜索
- 快捷服务
- 四类服务宫格
- 常用服务
- 附近服务
- AI 提醒
- 社区动态

内容很多，但“附近服务”目前只有地图入口，没有直接展示距离最近的服务点，用户需要多点一步才能获得地图价值。

#### 地图展示空间偏小

当前地图高度为 `420rpx`，分类条和图例占据地图上下空间。对“实时地图 + 附近服务”的产品定位来说，地图应成为页面主体，而不是一张普通卡片。

#### AI 语音入口与能力不一致

AI 助手中已有麦克风按钮，但当前 `onVoice()` 只是提示“语音输入暂未开通”。赛事演示时容易被评委点击后发现功能不完整。短期应隐藏或明确标注“规划中”，中长期再按 AI 方言方案接入。

#### 版本展示不一致

`pages/profile/index.wxml` 中仍硬编码显示 `1.4`，而项目当前版本为 `v1.2.7`。这类文案会削弱交付可信度，应在体验优化时统一从 `APP_VERSION` 读取或由页面数据注入。

### 2.4 本次审计的总体判断

当前项目功能面很广，但存在明显的“页面数量增长快、公共能力沉淀慢”问题。下一阶段不建议继续堆新页面，而应：

1. 用地图把“附近服务、报修位置、通知地点、活动地点”串起来；
2. 把重复的服务页收敛成少量页面模板；
3. 统一页头、卡片、表单、弹层和状态反馈；
4. 用真实数据替换或隐藏静态演示数据；
5. 在赛事演示路径上减少点击层级。

## 3. 居民端实时地图产品设计

### 3.1 产品定位

地图不是独立炫技功能，而是居民端所有“位置相关服务”的统一入口：

```text
我在这里
→ 最近的服务点在哪里
→ 怎么过去
→ 这个服务点现在能不能用
→ 我能不能在这里报修、签到或参加活动
```

### 3.2 双轨模式

#### 模式 A：基础地图模式

不需要任何定位接口权限，始终可用：

- 用户手动选择楼栋或出入口；
- 地图显示用户所选位置；
- 显示 9 个社区服务点；
- 按距离和步行时间排序；
- 可打开微信内置地图导航；
- 可离线使用本地配置。

适合：

- 微信接口未获批；
- 用户拒绝授权；
- 用户关闭手机定位；
- 赛场网络不稳定；
- 老年用户不熟悉定位授权。

#### 模式 B：实时定位模式

用户主动点击「定位到我的位置」后才触发：

- 请求位置授权；
- 获取当前位置；
- 地图中心移动到当前位置；
- 显示用户定位点；
- 重新计算附近服务点距离；
- 用户可点击「跟随移动」开启前台连续定位；
- 离开地图页立即停止更新。

适合：

- 接口权限已通过；
- 用户主动同意；
- 用户正在社区内寻找服务点或提交报修位置。

### 3.3 推荐交互流程

```text
打开社区地图
→ 默认显示上次手选楼栋或社区中心
→ 顶部显示「定位到我的位置」
→ 用户点击
→ 检查隐私授权和位置授权
→ 定位成功：地图移动到当前位置 + 显示定位点
→ 定位失败：保留手选点 + 提示「可继续手动选择楼栋」
→ 用户开启「跟随移动」
→ 页面可见期间更新位置
→ 离开页面自动停止
```

### 3.4 首期地图功能

1. **我的位置**
   - 一键定位；
   - 显示精度提示，如“约 20 米”；
   - 定位失败自动回到手选楼栋。

2. **附近服务点**
   - 物业服务中心；
   - 社区卫生服务站；
   - 社区活动室；
   - 社区食堂；
   - 快递柜；
   - 共享雨伞；
   - 充电宝；
   - 垃圾分类点；
   - 后续可增加 AED、无障碍通道、公共卫生间、饮水点、避雨点。

3. **分类筛选**
   - 全部；
   - 办事服务；
   - 便民设备；
   - 生活配套；
   - 应急设施。

4. **点位详情**
   - 名称；
   - 距离；
   - 步行时间；
   - 开放时间；
   - 当前状态；
   - 一键拨号；
   - 内置地图导航。

5. **地图/列表双视图**
   - 地图用于空间判断；
   - 列表用于长者、视力障碍用户和网络较差场景；
   - 两个视图共用同一批点位和排序。

6. **地图快捷提问**
   - “最近的卫生服务站在哪？”
   - “哪里有 AED？”
   - “怎么去社区食堂？”
   - AI 回答后附带「在地图中查看」按钮。

7. **报修位置辅助**
   - 报修时可选择楼栋或在地图上选点；
   - 默认只保存用户确认后的位置点；
   - 不自动上传连续轨迹。

8. **活动/志愿签到（可选）**
   - 活动详情显示签到范围；
   - 用户到达活动室附近后点击签到；
   - 首期只判断是否在预设范围内；
   - 不展示居民实时位置给其他用户。

### 3.5 不建议首期做的功能

- 后台持续定位；
- 居民互相查看实时位置；
- 家属长期追踪老人轨迹；
- 无期限保存位置历史；
- 自动上传完整移动轨迹；
- 依赖第三方地图完成后台定位；
- 使用定位数据做广告或商业画像。

地图“实时”不等于“持续监控”。赛事版本应以“用户主动使用、页面可见、用完即停”为原则。

## 4. 免费 API 与接口选型

### 4.1 能力对比

| 能力 | 推荐方案 | 是否需第三方 Key | 费用与限制 | 结论 |
| --- | --- | --- | --- | --- |
| 地图底图、marker、气泡、缩放 | 微信原生 `<map>` | 不需要 | 微信内置组件 | 首选 |
| 打开位置并导航 | `wx.openLocation` | 不需要 | 微信内置地图 | 首选 |
| 获取一次当前位置 | `wx.getLocation` | 不需要 | 免费，但需申请接口权限和用户授权 | 条件启用 |
| 前台持续定位 | `wx.startLocationUpdate` + `wx.onLocationChange` | 不需要 | 免费，但需申请权限，耗电更高 | 可选 |
| 两点距离/步行估算 | 本地 Haversine | 不需要 | 完全免费、离线可用 | 首选 |
| 社区点位展示 | 本地配置或云数据库 | 不需要 | 免费 | 首选 |
| 逆地址解析、社区外 POI 搜索、关键词联想 | 腾讯位置服务 WebService/JS SDK | 需要 Key | 有免费配额，具体以控制台当期规则为准 | 可选增强 |
| 百度地图 API | 百度开放平台 | 需要 Key | 需额外域名、SDK、坐标转换 | 不推荐首期 |

### 4.2 首选方案：零第三方地图 Key

首期建议只使用：

```text
微信原生 map
+ wx.openLocation
+ 本地 POI 配置
+ 本地 Haversine 距离
+ 可选 wx.getLocation
```

原因：

- 社区只有 1 个小区，9 个左右点位足够；
- 不需要反查外部地址；
- 不需要搜索社区外商户；
- 不需要调用付费地图接口；
- 不产生额外地图服务账单；
- 定位失败仍能用楼栋手选完成全部业务；
- 数据留在本地或微信云环境内。

### 4.3 腾讯位置服务的可选使用场景

只有出现以下需求时才建议接入：

- 根据经纬度反查“某某路 88 号”；
- 搜索社区周边医院、药店、公交站；
- 输入关键词自动补全地点；
- 计算驾车/公交路线；
- 展示社区外部的公共设施。

接入方式建议：

1. 腾讯位置服务控制台申请 Key；
2. 只开通实际需要的 WebService 能力；
3. Key 不写入前端源码，放到云函数环境变量；
4. 由云函数代理请求，前端不直接暴露 Key；
5. 设置每日调用上限与缓存；
6. 赛事版本可限制为每天几十次增强查询，普通地图浏览不调用。
7. 如非必要，不接入。

### 4.4 百度地图结论

百度地图可以作为备选，但不建议用于本项目首期：

- 需要额外申请 Key；
- 可能需要配置业务域名；
- 百度使用 BD-09 坐标系，需要与微信 GCJ-02 做转换；
- 多引入一套 SDK 和错误处理；
- 对社区内固定点位没有明显收益；
- 不能绕过微信位置权限。

因此，本项目地图供应商优先级为：

```text
微信原生地图
> 腾讯位置服务（可选）
> 百度地图（备选，不推荐首期）
> 其他第三方地图（不优先）
```

## 5. 微信官方接口申请与配置

### 5.1 是否需要申请

需要区分两类能力：

| 能力 | 是否需要微信官方申请 |
| --- | --- |
| 只显示静态地图、marker、气泡 | 不需要额外申请第三方 Key |
| 打开微信内置地图查看点位 | `wx.openLocation` 可直接使用 |
| 获取手机当前位置 | 需要位置接口权限、用户授权和隐私声明 |
| 前台实时更新位置 | 需要 `startLocationUpdate`、`onLocationChange` 接口权限 |
| 后台持续定位 | 需要更强权限，本项目不申请、不使用 |

微信官方文档说明：

- `wx.getLocation`、`wx.startLocationUpdate`、`wx.onLocationChange` 等地理位置接口，仅对符合条件的类目开放；
- 需要先通过类目审核，再到小程序管理后台「开发 → 开发管理 → 接口设置」中自助开通；
- 未开通时，代码审核可能被拦截；
- 使用这些接口必须在 `app.json` 中声明 `requiredPrivateInfos`；
- 需要用户授权 `scope.userLocation`；
- 调用前还必须满足微信用户隐私保护要求。

### 5.2 当前项目状态

当前 `miniprogram/app.json`：

- 没有 `requiredPrivateInfos`；
- 没有 `permission.scope.userLocation`；
- 当前地图页没有 `show-location`；
- 当前没有 `wx.getLocation`、`wx.startLocationUpdate` 调用；
- `tests/location-policy.test.ts` 有反向守卫，防止未经许可重新加入定位。

这说明 v1.2.7 当前是“手选位置保底版”，新方案需要在一个独立功能分支中重新打开定位能力。

### 5.3 申请前确认

1. 在微信公众平台确认小程序主体类型和服务类目。
2. 当前项目资料显示类目为「工具 > 信息查询」。
3. 微信官方开放类目中包含「工具 > 天气、信息查询、办公、设备管理」等位置相关工具场景。
4. 但 2026-10-24 本项目 `wx.getLocation` 已被驳回一次，因此不能仅凭类目判断一定能通过。
5. 重新申请时应先完成可演示的社区地图功能，再提交场景截图、操作路径和说明，而不是只写“居民定位”。

### 5.4 建议申请的接口

首期只申请：

```text
wx.getLocation
```

如果确实需要页面打开期间的实时移动：

```text
wx.startLocationUpdate
wx.onLocationChange
```

不申请：

```text
wx.startLocationUpdateBackground
```

理由：

- 后台定位权限更敏感；
- 赛事演示不需要后台追踪；
- 容易增加隐私风险和审核难度；
- 前台定位已经足够完成社区地图导航。

### 5.5 申请场景说明模板

可在接口申请中使用以下表述，按后台字段长度调整：

> 本小程序为非盈利社区便民工具，仅在用户主动打开社区地图或提交报修位置时读取当前位置，用于显示当前位置、计算附近物业服务点/卫生服务站/活动室距离并打开微信内置地图导航。位置仅用于本次社区服务，不保存移动轨迹，不做后台定位，不向其他居民展示实时位置，不用于广告或商业用途。

申请材料建议附：

1. 首页「附近服务」入口截图；
2. 地图页「定位到我的位置」按钮截图；
3. 定位失败后手选楼栋的降级截图；
4. 点击服务点后导航的截图；
5. 隐私授权弹窗截图；
6. 一段 30 秒以内的演示视频；
7. 功能路径说明：首页 → 社区地图 → 定位 → 附近服务点 → 导航。

### 5.6 审核通过后的配置

通过后再添加，不要提前写入正式版本：

```json
{
  "requiredPrivateInfos": [
    "getLocation",
    "onLocationChange",
    "startLocationUpdate"
  ],
  "permission": {
    "scope.userLocation": {
      "desc": "用于社区地图定位和附近服务导航"
    }
  }
}
```

注意：

- `desc` 要简短、真实、与实际场景一致；
- 不要写“持续追踪”“实时共享”等扩大范围的表述；
- 没有使用连续定位时，不要声明 `onLocationChange` 或 `startLocationUpdate`；
- 上线版本必须与实际调用的接口保持一致；
- 申请未通过时保持当前 `app.json` 不声明定位。

### 5.7 隐私保护指引

如果启用定位，需要在微信公众平台的《用户隐私保护指引》中补充：

- 位置信息；
- 使用目的：显示当前位置、附近服务点距离和社区内导航；
- 使用场景：用户主动打开社区地图或选择报修位置；
- 保存期限：默认不在云端保存；
- 是否共享：不向其他居民公开，不用于广告；
- 用户权利：可拒绝授权、可手动选择楼栋、可关闭定位。

同时同步更新项目内：

- 首启页隐私说明；
- 欢迎页隐私说明；
- 登录页隐私说明；
- 地图页底部提示；
- 报修页位置说明。

### 5.8 审核失败后的处理

如果重新申请仍不通过：

1. 不发布依赖定位的版本；
2. 保持手选楼栋模式；
3. 保留地图静态展示、距离和导航；
4. 在赛事材料中如实说明“微信定位接口未开放，采用楼栋级手选方案”；
5. 不用第三方 API 规避微信定位限制；
6. 不伪造定位成功截图；
7. 可使用腾讯位置服务做地图展示增强，但设备位置仍以微信接口为准。

## 6. 隐私与数据安全

### 6.1 默认不保存位置

首期规定：

```text
位置计算在手机本地完成
不把连续坐标写入云数据库
不保存移动轨迹
不向其他居民展示实时位置
不在日志里打印经纬度
```

### 6.2 最小化上传

只有在用户明确提交以下业务时才允许上传位置：

- 报修位置；
- 活动签到；
- 志愿服务签到；
- 用户主动选择的社区服务点。

上传内容建议只保留：

```text
点位名称
经纬度（可选）
精度（可选）
用户确认时间
业务关联 ID
```

不上传：

- 连续定位序列；
- 后台移动轨迹；
- 与业务无关的常去地点；
- 长期位置画像。

### 6.3 权限被拒绝

用户拒绝定位时必须：

- 不白屏；
- 不反复弹授权；
- 自动保留手选楼栋；
- 提示“可继续手动选择位置”；
- 提供“去设置”入口；
- 地图仍可浏览和导航。

### 6.4 关怀模式

地图页在关怀模式下：

- 地图高度不压缩；
- “定位”“返回”“导航”按钮至少 88rpx；
- 分类按钮不重叠；
- 底部点位卡字号放大；
- 允许切换列表模式；
- 不依赖精确拖动地图完成操作。
