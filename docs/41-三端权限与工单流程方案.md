> 关联文档：`39-客户端与后台管理端双端方案.md`（历史稿）、`40-AI识图与方言转换方案.md`

## 1. 结论先行

本项目采用：

> **同一个小程序、三个登录页签、三套页面壳层、服务端统一鉴权。**

三个登录页签固定为：

```text
[ 居民 / 家长 ]    [ 管理端 ]    [ 维修端 ]
```

核心结论：

1. 默认进入居民端，不默认进入管理端或维修端。
2. 管理端由 `property / admin / super_admin` 登录；维修端由 `maintenance` 登录。
3. 前端只负责展示与跳转，最终权限必须由云函数按服务端会话和角色判断。
4. 首期只服务一个社区，不做多社区隔离，不做独立 Web 后台。
5. 首期管理端只做在线查看，不做 Excel 导出和批量导入。
6. 首期包含圈子审核和 AI 数据复核。
7. 工单全部分类合计，每名维修人员最多同时处理 **3 单**。
8. 工单最终确认后立即锁定，只能等待居民在 7 天反馈期内反馈。
9. 居民反馈“未解决”时创建关联的新返工工单，并从抢单池重新开始。
10. 同一根工单最多允许 **5 次返工循环**，即最多 6 个工单周期，之后转人工处理。

## 2. 三端形态与登录

### 2.1 端形态

```text
微信小程序启动
      │
      ▼
三页签登录页
      │
      ├── 居民 / 家长（默认）
      │       │
      │       ▼
      │   微信身份识别 + 首启资料
      │       │
      │       ▼
      │   居民端首页
      │
      ├── 管理端
      │       │
      │       ▼
      │   工作人员账号 + 密码
      │       │
      │       ▼
      │   物业 / 管理员 / 超级管理员工作台
      │
      └── 维修端
              │
              ▼
        维修人员账号 + 密码
              │
              ▼
        抢单大厅 / 我的工单
```

### 2.2 登录页规则

- 页面默认选中「居民 / 家长」。
- 点击「管理端」后才显示工作人员账号、密码输入框。
- 点击「维修端」后才显示维修人员账号、密码输入框。
- 三个端不共用同一个本地登录状态。
- 工作人员和维修人员退出后，统一回到三页签登录页，并恢复默认居民页签。
- 管理端和维修端不得通过修改本地 storage、页面参数或前端变量直接进入。
- 登录失败必须限流；连续失败 5 次锁定 15 分钟。

### 2.3 端标识

建议统一定义：

```text
portalMode = resident | management | maintenance
```

进入页面时同时校验：

1. 当前 `portalMode`；
2. 服务端工作人员或维修人员会话；
3. 服务端角色；
4. 当前账号状态；
5. 被访问工单或数据是否在当前账号权限范围内。

服务端不得信任前端传入的 `role`、`isAdmin`、`portalMode` 等权限字段。

## 3. 角色与权限

### 3.1 角色定义

| 角色 | 说明 | 所属端 |
| --- | --- | --- |
| `resident` | 普通居民 | 居民端 |
| `guardian` | 已绑定未成年人的监护人 | 居民端 |
| `property` | 物业工作人员 | 管理端 |
| `admin` | 社区管理员 | 管理端 |
| `super_admin` | 超级管理员 | 管理端 |
| `maintenance` | 维修人员 | 维修端 |

### 3.2 角色职责

#### 物业 `property`

- 只能把待放单工单放入抢单池，不能指定维修人员。
- 不允许抢单。
- 可补充工单记录。
- 可审批维修人员提交的释放申请。
- 可验收维修完工。
- 验收不通过时，必须填写退回说明或上传退回照片。
- 验收不通过后，工单直接退回原维修人员的 `processing` 状态。
- 查看居民手机号时始终脱敏。
- 不能查看维修人员的密码、会话等敏感凭据。
- 管理员最终确认后，不能再补充备注、上传附件或修改工单。

#### 管理员 `admin`

- 查看全部工单、居民资料、圈子审核和 AI 数据复核。
- 可查看居民完整手机号和维修人员完整手机号。
- 负责工单最终确认。
- 不参与抢单、放单和手动指定维修人员。
- 可查看释放申请审批记录。
- 可处理超时工单和异常工单。
- 管理员最终确认后，原工单立即锁定。

#### 超级管理员 `super_admin`

- 拥有管理员的全部权限。
- 唯一可新增、禁用、重置工作人员和维修人员账号的角色。
- 可配置维修人员技能、服务分类和超时提醒参数。
- 首个超级管理员通过部署脚本或云控制台初始化。
- 超级管理员不得在数据库中保存明文密码。

#### 维修人员 `maintenance`

- 从抢单池抢单。
- 全部分类合计最多同时处理 3 单。
- 抢单成功后，仅能查看该工单相关居民的完整手机号。
- 必须上传维修前照片、维修后照片和处理说明才能提交完工。
- 不能主动释放工单，只能提交释放申请。
- 释放申请必须填写原因并上传至少 1 张现场照片。
- 释放申请未审批前，该工单仍计入 3 单上限。
- 工单最终确认后，立即失去该工单居民完整手机号权限。
- 管理员最终确认后，不能再补充备注或上传附件。

### 3.3 手机号可见性

| 查看者 | 居民手机号 | 维修人员手机号 |
| --- | --- | --- |
| 居民本人 | 完整 | 不适用 |
| 监护人 | 仅绑定对象完整 | 不适用 |
| 物业 | 脱敏 | 按最小必要原则显示；需要联系时优先使用系统内一键拨号 |
| 管理员 | 完整 | 完整 |
| 超级管理员 | 完整 | 完整 |
| 维修人员 | 仅当前关联工单完整，最终确认后收回 | 本人完整 |

维修人员可查看居民完整手机号的状态仅限：

```text
assigned
processing
worker_done
release_requested
```

工单进入 `closed` 后立即收回，不得通过历史缓存、日志或接口继续查看。

### 3.4 首期功能边界

首期包含：

- 居民报修；
- 物业放单；
- 维修人员抢单与处理；
- 物业验收；
- 管理员最终确认；
- 居民 7 天反馈；
- 关联返工循环；
- 超时提醒；
- 圈子审核；
- AI 数据复核；
- 在线查看，不提供 Excel 导出。

首期不做：

- 多社区；
- 独立 Web 管理后台；
- 批量导入导出；
- 自动派单；
- 管理员指定维修人员；
- 维修人员主动释放；
- 物业抢单；
- 居民在最终反馈中补充图片或文字。

## 4. 工单状态机

### 4.1 状态定义

| 状态 | 中文名称 | 说明 |
| --- | --- | --- |
| `pending_dispatch` | 待放单 | 居民已提交，等待物业放入抢单池 |
| `pool` | 抢单池 | 等待维修人员抢单 |
| `assigned` | 已接单 | 维修人员已抢单，尚未开始处理 |
| `processing` | 处理中 | 维修人员正在处理，或验收退回后重新处理 |
| `worker_done` | 维修完工 | 维修人员已提交前后照片和处理说明 |
| `property_verified` | 物业已验收 | 物业验收通过，等待管理员最终确认 |
| `closed` | 已最终确认 | 管理员确认完成，原工单锁定并进入居民反馈期 |
| `release_requested` | 释放申请中 | 维修人员申请释放，等待物业审批 |
| `canceled` | 已取消 | 特殊异常处置状态，需理由和审计；首期可暂不开放 |

### 4.2 正常流转

```text
居民提交
→ pending_dispatch
→ 物业放入抢单池
→ pool
→ 维修人员抢单
→ assigned
→ 维修人员开始处理
→ processing
→ 维修人员提交前后照片和处理说明
→ worker_done
→ 物业验收通过
→ property_verified
→ 管理员最终确认
→ closed
```

### 4.3 验收回退

```text
property_verified 之前，物业验收不通过
→ 原工单直接回到原维修人员的 processing
```

规则：

- 不新建工单，不重新进入抢单池。
- 必须填写退回说明或上传退回照片，至少提供一种。
- 原维修人员继续处理，不重新计算抢单次数。
- 退回记录、照片和操作人全部写入工单时间线。
- 退回后仍计入该维修人员的 3 单上限。

### 4.4 释放申请

```text
assigned / processing / worker_done
→ 维修人员提交释放申请
→ release_requested
→ 物业审批
```

物业批准：

```text
release_requested
→ pool
```

- 工单回到抢单池，原维修人员释放一个处理名额。
- 记录释放原因、照片、申请人、审批人和审批时间。
- 管理员可查看备案，但不参与抢单和指派。

物业拒绝：

```text
release_requested
→ processing
```

- 原维修人员继续处理。
- 拒绝原因必须填写。
- 释放申请、批准或拒绝均写审计日志。
- 维修人员不能自行把状态改回 `processing` 或主动释放。

### 4.5 抢单并发约束

每名维修人员的处理中名额按全部分类合计：

```text
assigned
+ processing
+ worker_done
+ release_requested
<= 3
```

抢单必须由服务端原子校验：

1. 当前账号为有效维修人员；
2. 工单当前状态为 `pool`；
3. 该账号未达到 3 单上限；
4. 工单未被其他维修人员抢走；
5. 技能与服务分类符合要求。

任意条件不满足时拒绝抢单，不能只依赖前端按钮置灰。

## 5. 最终确认后的锁定与返工循环

### 5.1 最终确认即时锁定

管理员最终确认后，工单进入 `closed` 并立即：

- 锁定原工单的处理记录、回访记录和附件；
- 物业、维修人员不能再补充备注；
- 物业、维修人员不能再上传图片或修改处理说明；
- 维修人员立即失去居民完整手机号权限；
- 保留管理员、物业和维修人员的既有历史记录供审计；
- 写入 `finalConfirmedAt`、`finalConfirmedBy` 和 `lockedAt`。

### 5.2 居民反馈期

每个周期最终确认后，居民拥有 **7 天** 反馈期。

居民端只提供两个反馈按钮：

```text
[ 已解决 ]    [ 未解决 ]
```

- 不需要居民填写文字；
- 不需要居民上传图片；
- 不允许居民在反馈中追加附件；
- 系统记录反馈时间、反馈结果和对应工单；
- 反馈截止前 1 天提醒居民；
- 7 天内未反馈，反馈状态自动记为 `feedback_expired`，原工单进入归档状态；
- 居民不能通过修改前端状态伪造反馈，反馈必须由服务端写入。

建议独立维护反馈状态：

```text
feedback_pending
feedback_resolved
feedback_rework
feedback_expired
feedback_manual_required
```

### 5.3 居民反馈“已解决”

```text
closed + feedback_pending
→ 居民点击“已解决”
→ feedback_resolved
→ 原工单归档
```

- 不新建工单。
- 原工单保持锁定。
- 记录 `feedbackAt`。
- 后续仅管理员可查看历史。

### 5.4 居民反馈“未解决”

```text
closed + feedback_pending
→ 居民点击“未解决”
→ 创建关联的新工单
→ 新工单直接进入 pool
```

规则：

- 新工单不重新回到 `pending_dispatch`，直接从抢单池开始。
- 新工单继承原工单的社区、地点、分类、问题描述和必要附件。
- 新工单必须记录：
  - `rootWorkorderId`：根工单；
  - `parentWorkorderId`：上一周期工单；
  - `cycleNo`：当前周期号；
  - `reworkCount`：已发生的返工次数。
- 原工单继续保留完整历史，不覆盖、不复用、不重新打开。
- 新工单重新经历抢单、处理、验收、最终确认和 7 天反馈。
- 新工单不能自动回到原维修人员，必须重新从抢单池抢单。

### 5.5 周期与上限

- 初次报修：`cycleNo = 1`。
- 第一次返工：`cycleNo = 2`。
- 最多允许 5 次返工，因此最大 `cycleNo = 6`。
- 返工次数达到 5 次后，即使居民再次反馈“未解决”，也不再自动创建第 6 次返工工单。
- 达到上限时：
  - 反馈状态写为 `feedback_manual_required`；
  - 同时提醒物业、管理员和超级管理员；
  - 页面提示“已达到自动返工上限，请转人工处理”；
  - 进入线下协调或人工服务流程；
  - 不允许通过重复点击绕过上限。

### 5.6 历史链展示

工单详情应提供：

```text
根工单 → 周期 1 → 周期 2 → ... → 当前周期
```

每个周期只读展示：

- 工单编号；
- 维修人员；
- 物业验收人；
- 管理员最终确认人；
- 关键时间；
- 前后照片；
- 处理说明；
- 退回说明；
- 释放审批记录；
- 居民反馈结果。

## 6. 超时提醒统一设置

### 6.1 配置方式

超时提醒采用统一配置，不写死在页面代码中：

- 统一在管理端「系统设置 → 超时提醒」维护；
- 超级管理员可修改；
- 管理员可查看；
- 建议保存到 `system_settings`，并保留修改审计；
- 默认采用下表建议值；
- 可按社区统一调整，不针对单个工单单独设置；
- 提醒渠道以小程序内消息和微信订阅消息为主；
- 同一工单同一节点 30 分钟内去重，避免重复轰炸；
- 达到阈值后提醒责任人，继续超时则升级提醒管理员。

> 说明：本方案将“统一设置”定义为“统一配置中心维护阈值，默认采用建议值”，不是把所有节点硬编码成同一个分钟数。

### 6.2 默认阈值

| 节点 | 默认阈值 | 首次提醒对象 | 升级提醒对象 |
| --- | ---: | --- | --- |
| 报修后物业未放单 | 30 分钟 | 物业 | 管理员 |
| 抢单池无人接单 | 60 分钟 | 物业 | 管理员 |
| 已接单未开始处理 | 60 分钟 | 维修人员 | 物业、管理员 |
| 普通工单处理中未完工 | 4 小时 | 维修人员 | 物业、管理员 |
| 紧急工单处理中未完工 | 1 小时 | 维修人员 | 物业、管理员 |
| 维修完工后物业未验收 | 2 小时 | 物业 | 管理员 |
| 物业验收后管理员未确认 | 4 小时 | 管理员 | 超级管理员 |
| 释放申请未审批 | 30 分钟 | 物业 | 管理员 |
| 居民反馈截止前 | 提前 1 天 | 居民 | 居民端站内提醒 |
| 居民反馈期结束 | 7 天 | 系统自动归档 | 无需升级 |

### 6.3 提醒内容

统一提醒字段：

- 工单编号；
- 当前状态；
- 已停留时长；
- 超时节点；
- 责任角色；
- 下一步动作；
- 工单详情跳转入口。

提醒记录写入通知任务表，失败可重试，但不得因通知失败影响工单主流程。

## 7. 页面与导航设计

### 7.1 登录与居民端

```text
pages/auth/entry/index                 三页签登录入口
pages/auth/setup/index                 居民首启资料
pages/workorder/create/index           居民报修
pages/workorder/detail/index           居民工单详情
pages/workorder/feedback/index         居民 7 天反馈
```

居民端新增反馈页只展示：

- 工单摘要；
- 最终处理结果；
- 7 天倒计时；
- 「已解决」按钮；
- 「未解决」按钮；
- 超过返工上限时的转人工提示。

不展示文字反馈输入框和图片上传入口。

### 7.2 管理端导航

```text
工作台 / 工单 / 居民 / 内容 / 管理
```

| 导航 | 主要页面 |
| --- | --- |
| 工作台 | 待放单、抢单池、超时工单、待验收、待最终确认、居民未解决反馈 |
| 工单 | 全部工单、工单详情、退回记录、释放审批、周期链 |
| 居民 | 居民档案、监护人关系、关怀标签、手机号脱敏查看 |
| 内容 | 圈子审核、举报处理、AI 数据复核 |
| 管理 | 账号管理、维修技能、超时提醒、审计日志、系统设置 |

建议页面目录：

```text
pages/management/login/index              管理端登录（可与三页签共用）
pages/management/home/index               工作台
pages/management/workorders/index         工单列表
pages/management/workorder-detail/index   工单详情
pages/management/residents/index          居民列表
pages/management/resident-detail/index    居民详情
```

## 8. 账号、安全与审计

### 8.1 账号创建

- 只有超级管理员可以创建物业、管理员和维修人员账号。
- 居民不能自助注册工作人员或维修人员账号。
- 初始密码由系统随机生成，仅首次展示一次。
- 首次登录强制修改密码。
- 账号与工作人员姓名、手机号、角色、技能和状态绑定。
- 一个账号只能有一个主角色；如需一人多职，后续再扩展多角色。

### 8.2 会话安全

- 密码使用 `scrypt` 或 `bcrypt` 加盐哈希。
- 禁止在数据库、日志、源码和前端缓存中保存明文密码。
- 会话令牌只保存哈希，设置过期时间。
- 管理端和维修端使用独立会话作用域。
- 退出登录立即销毁会话。
- 禁用账号时使其所有会话立即失效。
- 超级管理员可强制下线账号。

### 8.3 数据与隐私

- 居民手机号按角色最小化展示。
- 物业查看居民手机号脱敏。
- 维修人员仅在当前关联工单的生命周期内查看完整手机号。
- 管理员可查看居民和维修人员完整手机号。
- 查看完整手机号、导出类操作和账号管理写审计日志。
- 首期不提供 Excel 导出，避免批量带走数据。
- AI 识图、语音和聊天数据只允许留在微信/腾讯云生态内。
- 密钥只配置在云函数环境变量中，源码零明文。

### 8.4 审计事件

至少记录：

```text
staff_login_success
staff_login_failed
staff_logout
account_created
account_disabled
password_reset
workorder_dispatched_to_pool
workorder_claimed
workorder_started
workorder_release_requested
workorder_release_approved
workorder_release_rejected
workorder_completed
workorder_returned
workorder_property_verified
workorder_final_confirmed
resident_feedback_resolved
resident_feedback_rework_created
workorder_feedback_expired
workorder_manual_required
phone_number_viewed
ai_review_updated
circle_content_moderated
timeout_settings_updated
```

审计日志必须包含操作人、角色、操作时间、工单或对象 ID、动作、变更前后摘要和请求来源摘要。

## 12. 验收标准

### 12.1 登录与权限

- 默认进入居民端；
- 三个登录页签可正常切换；
- 普通居民无法进入管理端和维修端；
- 物业不能抢单或指定维修人员；
- 维修人员不能进入管理端；
- 服务端拒绝伪造角色和会话；
- 账号连续失败达到阈值后锁定；
- 首次登录强制改密。

### 12.2 工单处理

- 居民可正常提交报修；
- 物业可把待放单工单放入抢单池；
- 维修人员抢单原子成功，不会重复抢单；
- 每名维修人员全部分类合计不超过 3 单；
- 维修人员提交完工必须包含前后照片和处理说明；
- 物业验收通过后等待管理员确认；
- 物业退回后直接回到原维修人员 `processing`；
- 退回说明或照片至少提供一种；
- 维修人员释放必须经物业审批；
- 物业拒绝释放后工单回到 `processing`；
- 所有关键操作写入时间线和审计日志。

### 12.3 最终确认与反馈

- 管理员最终确认后工单立即锁定；
- 物业和维修人员无法继续补充备注或上传附件；
- 维修人员立即失去居民完整手机号权限；
- 居民有 7 天反馈期；
- 居民反馈只有“已解决”和“未解决”；
- 不需要居民填写文字或上传图片；
- “未解决”创建关联的新工单；
- 新工单从抢单池开始；
- 同一根工单最多 5 次返工；
- 超过上限后不能自动创建第 6 次返工并提示转人工；
- 反馈截止前 1 天提醒；
- 7 天未反馈自动归档。

### 12.4 超时提醒

- 超时阈值统一在管理端设置；
- 默认值按本方案执行；
- 超时后提醒责任角色；
- 继续超时升级提醒管理员；
- 同一工单同一节点不会短时间重复轰炸；
- 通知失败不阻塞工单主流程。

### 12.5 手机号与隐私

- 物业查看居民手机号脱敏；
- 管理员可查看居民和维修人员完整手机号；
- 维修人员只在负责工单的有效状态内查看居民完整手机号；
- 最终确认后立即收回；
- 查看完整手机号写审计日志；
- 首期不提供 Excel 导出；
- 密钥不出现在源码和日志中。

### 12.6 管理端首版

- 工作台展示待放单、超时、待验收、待确认和未解决反馈；
- 工单支持筛选和周期链查看；
- 圈子审核可用；
- AI 数据复核可用；
- 账号管理仅超级管理员可用；
- 所有后台页面只读和操作权限符合角色矩阵。
