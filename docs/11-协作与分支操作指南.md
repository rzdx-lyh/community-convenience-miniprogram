## 1. 分支模型（轻量 GitHub Flow）

| 分支 | 用途 | 谁推 |
|---|---|---|
| `main` | **稳定分支**，只接受 PR 合并，不直接提交 | 你（合并） |
| `feature/<模块>-<功能>` | 一个功能一条，一人一条 | 各自 |
| 临时分支 | 实验性改动，随时删 | 各自 |

流程：**建分支 → 开发 → 自测 → push → 开 PR → review → 合并 main → 删分支**。

---

## 2. 开工前：契约先行（本项目已有的好习惯）

- 新功能若涉及**接口/数据**：先在 `contracts/api-contract.md` / `contracts/db-schema.md` 定好，登记 `contracts/契约变更记录.md`，**冻结后再分头写代码**。
- 好处：两个同学各写各的，不会因为字段名/参数不一致而返工。

---

## 3. 功能区域怎么分（避免冲突的核心）

**按"目录 / 云函数 / 集合"划片，不要按"同一文件里各写一半"划。**

| 划分维度 | 建议 |
|---|---|
| 前端 | 一个同学负责若干 `pages/xxx/*` + 相关组件 |
| 后端 | 另一个同学负责若干 `cloudfunctions/xxx/*` |
| 共享文件 | `contracts/`、`utils/request.ts`、`shared/*`、`app.json` **改动必须先说一声**，最好由你统一改 |

**示例分工**

| 同学 | 分支 | 负责区域 |
|---|---|---|
| A | `feature/notice-push` | `miniprogram/pages/notice/*` + `services/notice.ts` |
| B | `feature/qa-voice` | `cloudfunctions/qa/*` + `shared/ai.js` |
| 你 | `feature/index-v2` | `miniprogram/pages/index/*` |

> ⚠️ 两人改**同一个文件** = 必冲突。拆分到不同文件/目录是避免冲突最有效的手段。

## 4. 两位同学的操作（可直接抄）

```bash
# ① 克隆
git clone https://github.com/rzdx-lyh/community-convenience-miniprogram.git
cd community-convenience-miniprogram

# ② 首次可能需要关校验（若遇到证书报错）
# git config http.sslVerify false

# ③ 建功能分支
git checkout main && git pull
git checkout -b feature/<模块>-<功能>

# ④ 开发……
npm install            # 首次
npm run verify         # 提交前门禁：typecheck + lint + test，必须全绿

# ⑤ 提交并推送
git add -A
git commit -m "feat(模块): 一句话说明"
git push -u origin feature/<模块>-<功能>

# ⑥ 到 GitHub 开 Pull Request → 等 review → 合并
```

**随时同步上游**（避免落后太久）：
```bash
git fetch origin
git rebase origin/main     # 或 git merge origin/main
```

## 6. 冲突与同步规范

1. **每天开工先 `git fetch origin && git rebase origin/main`**（或 merge），把冲突化解在本地。
2. 冲突处理：
   ```bash
   git fetch origin
   git rebase origin/main
   # 手工解冲突 → git add <文件> → git rebase --continue
   ```
3. **小步提交**（一个逻辑点一条），冲突面越小。
4. 契约 / 共享文件冲突 → **找你对齐**，不要各改各的。

---

## 7. 门禁与提交规范

- 每次 `git push` 前必须 `npm run verify` **全绿**（`tsc` + `eslint` + `vitest`）。
- commit message：`feat|fix|docs|chore(<scope>): <描述>`。
- **永不提交**：`node_modules/`、密钥/Key、`project.private.config.json`、页面级 `.js`（都是编译产物）。`.gitignore` 已兜底，别用 `-f` 强加。

## 8. 给 main 加保护规则（详细操作）

> ✅ **已开启（2026-10-16，经 API）**：`main` 要求 Pull Request（审批数 1）、禁止强推、禁止删除该分支；`enforce_admins=false` → **管理员（你本人）仍可直推**，**队友（普通协作者）必须走 PR**。
> 目的：**禁止队友直推 main**，所有改动走 PR，保证主分支随时可演示/可提交。

### 8.1 入口
`仓库 → Settings → Branches → Add branch protection rule`
（或新版：`Settings → Rules → Rulesets`，功能等价）

### 8.2 推荐配置

| 项 | 建议值 | 说明 |
|---|---|---|
| Branch name pattern | `main` | 规则作用分支 |
| ✅ Require a pull request before merging | 勾选 | **核心**：禁止直推 |
| └ Required approvals | `1` | 3 人团队建议 1 人审查；人少可设 0（仍保留 PR 流程） |
| └ Dismiss stale pull request approvals | 勾选 | 有新提交自动作废旧批准 |
| ⬜ Require status checks to pass | 暂不勾 | 等以后接了 CI（`npm run verify`）再勾 |
| ⬜ Require linear history | 可选勾 | 只允许 rebase/squash 合并，历史更干净 |
| ⬜ Do not allow bypassing the above settings | 先不勾 | 勾了**管理员也不能直推**（更严格，但你有紧急情况时会被卡） |
| ⬜ Lock branch | **不要勾** | 会把分支锁成只读，谁都不能推 |

点 **Create / Save changes** 生效。

### 8.3 生效后的行为
- 直接 `git push origin main` → **被拒绝**（提示 protected branch）。
- 正确流程：`feature 分支 → push → 开 PR → review → Merge`。
- 自己的紧急小改动：临时取消勾选 → 推 → 再勾回；或把 `main` 的 PR 自己合并（有效）。

### 8.4 注意事项
- **公开仓库免费**用该功能（本仓库是 public ✅）；个人账号的**私有仓库**需要 Pro。
- ⚠️ 开启后，**本机（含我）也无法再直推 main**——这正是预期效果，后续一律走 PR。
- 若只想"防误推"不想太严：只勾 `Require a pull request`，把 `Required approvals` 设为 `0`。

### 8.5 验证
```bash
# 应被拒绝（返回 protected branch 错误）
git push origin main
# 正确路径：
git checkout -b feature/test && git push -u origin feature/test
```
